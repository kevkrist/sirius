## Counting how often A blocks

Define A as the batch owning the first future awaited for a registry/stream cohort, not the first file submitted, first batch in the registry, or every member future. Record one cohort identity, A identity, live/open sibling count, source identity, device/stream, query/iteration and first-wait timestamp. Otherwise repeated slice futures inflate the denominator and singleton calls hide the relevant rate.

Two different observations are necessary:

- **Pending at first wait:** Does A have requested chunks that are loading under an in-flight prefetch at entry, before sibling issuance? This is the policy-independent opportunity indicator as observed in that particular run. Snapshot sibling pending status at the same phase too. Sampling all sources is not perfectly atomic; record this as an observation, not a counterfactual outcome guarantee.
- **Actual issue-side wait:** Did `await_inflight_prefetch()` take its wait branch when A or a sibling was issued, and how long was that wait? Siblings-first can allow A's prefetch to finish before A is issued, so issue-time status alone systematically hides the very overlap being tested. A call to the wait routine is not proof of a substantial stall; completion can race the observation. Keep count and wall-duration distribution separately.

Use the real wait predicate: valid handle plus a nonempty, in-bounds requested range overlapping a `chunk_state::loading` chunk **and** handle producer stage `loading`. Merely `is_prefetch_in_flight()` counts unrelated bytes and is not the branch predicate. The code waits for this handle's producer to stop loading, so readiness of one requested chunk does not by itself settle the handle. Record prepared/not-started/no-handle states separately from active loading.

Do not mutate cache state, call a blocking wait, consume registry entries twice, or change ownership/lock order while observing entry state. ## Why a real prefetch wait occurs

The source mechanism is narrower than generic disk latency: readahead has already started the handle's producer and claimed overlapping cache chunks, but its backend completion has not yet transitioned producer state from loading. Demand joins that producer in `await_inflight_prefetch()` to avoid a duplicate read/race. Local opportunistic readahead is triggered by non-scan deployments, which can yield a different pending frequency from eager remote readahead. To attribute a particular wait to queueing, device service, scheduling, or admission, correlate producer start, backend submission/completion and demand entry; the pending counter alone cannot distinguish those causes.

Sibling-first permits sibling work before entering A's blocking issue call. Own-first can prevent a blocked sibling from delaying A's initial submission, but still issues siblings before returning A's future. This is why source data-ready time and first-future return time remain different. Do not infer query benefit from source wait counts alone.
